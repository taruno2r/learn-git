01

Repository (repo)

The project folder, tracked by Git and hosted on GitHub et al.

What it does

A repository is your project folder plus a hidden .git directory. That directory is Git's database: every snapshot, branch and commit message ever recorded lives there. You have a local repo on your machine, and usually a remote copy on GitHub, GitLab or Bitbucket that everyone on the team syncs with.

git init                       # start tracking this folder
git remote add origin <url>    # link it to GitHub
git status                     # what's changed?

Considerations

  • Add a README that says what the project is and how to run it. It's the first thing people see.
  • Add a .gitignore early for build output, node_modules, .env files and OS junk like .DS_Store.
  • Never commit secrets. Once pushed, they live on in history. If one leaks, rotate it; deleting the file isn't enough.
  • Choose visibility (public or private) and a license on purpose. A public repo without a license isn't actually open source.

02

Clone

Download a copy of the code to your machine.

What it does

git clone downloads the whole repository: every file, every commit and every branch. It also sets up a remote called origin that points back to where you cloned from, so you can push and pull later. After that you work locally and offline. You don't need the internet until you sync.

git clone https://github.com/you/my-project.git
cd my-project
git log --oneline              # the full history is here

Considerations

  • Clone vs fork: a fork is your own copy on GitHub (for contributing to repos you can't push to). A clone is a copy on your machine. You often fork first, then clone your fork.
  • HTTPS vs SSH: once you set up SSH keys you won't need to type tokens.
  • For huge repos, git clone --depth 1 makes a shallow clone with just the latest snapshot.
  • Clone once. After that, git pull keeps you up to date. You don't need to re-clone.

03

Branch

A safe parallel timeline to the main codebase.

What it does

A branch is a lightweight, movable label that points at a commit. Creating one gives you a separate line of work. You can commit, experiment and break things there while main stays stable and keeps moving forward with other people's work. Switching branches swaps the files in your folder to match.

git switch -c feature/login    # create + switch
git branch                     # list branches
git switch main                # go back

Considerations

  • Keep branches short-lived and focused on one change. Long-running branches drift and end up with painful conflicts.
  • Use descriptive names, often with a prefix: feature/, fix/, docs/.
  • Branch from an up-to-date main: run git pull first.
  • Commit or stash your work before switching, and delete branches once they're merged.

04

Commit

A snapshot + message describing your changes.

What it does

A commit permanently records a snapshot of your staged files, along with an author, a timestamp, a message and a link to the commit before it. It gets a unique ID (a hash like a1b2c3d). The staging step (git add) lets you choose exactly which changes go into the snapshot, so one commit can hold one logical change.

git add index.html style.css   # stage
git diff --staged              # review what's staged
git commit -m "Add login form" # snapshot

Considerations

  • Make small, atomic commits: one idea each. They're easier to review, revert and understand later.
  • Write messages in the imperative ("Add", "Fix", "Remove"). Keep the subject to about 50 characters and use the body to explain why.
  • Review with git diff --staged before committing so you don't ship debug logs.
  • Commits are local until you push. Your teammates can't see them yet.

05

Push / Pull

Upload to / download from the hosted repository.

What it does

git push uploads the commits you made locally to the matching branch on the remote, so others can see them. git pull does the reverse: it fetches new commits from the remote and merges (or rebases) them into your current branch, bringing in your teammates' work.

git push origin main           # upload your commits
git pull                       # = git fetch + git merge
git fetch                      # download, but don't touch my files

Considerations

  • Pull before you start work and again before you push. It keeps conflicts small.
  • If a push is rejected, the remote has commits you don't have yet. Pull, resolve anything, then push again.
  • Avoid git push --force on shared branches because it can delete teammates' work. If you really must, use --force-with-lease.
  • The first push of a new branch needs git push -u origin <branch> to set its upstream.

06

Diff

The visual difference between two versions of code from two different branches.

What it does

A diff shows, line by line, what was removed (−) and what was added (+) between two versions. You can compare your unsaved edits against the last commit, staged changes, two commits or two whole branches. Pull requests on GitHub are built around the diff.

git diff                       # unstaged edits
git diff --staged              # what will be committed
git diff main feature/login    # compare two branches

Considerations

  • Read your own diff before every commit and PR. It's the cheapest code review there is.
  • Reformatting or whitespace changes make noisy diffs that hide real changes. Keep them in separate commits, or use git diff -w to ignore whitespace.
  • Smaller diffs get reviewed faster and more carefully.
  • Binary files like images and PDFs don't diff line by line, so GitHub shows image diffs visually instead.

07

Merge

Combine a branch back into another branch.

What it does

Merging takes the commits from one branch and joins them into another. If both branches have moved on, Git creates a merge commit with two parents that ties the histories together. If only your branch moved, Git simply fast-forwards the label. On GitHub this is usually the last step of a pull request.

git switch main
git pull                       # make sure main is current
git merge feature/login
git branch -d feature/login    # tidy up

Considerations

  • Merging keeps the true history: you can always see when a branch existed and when it landed.
  • GitHub offers three buttons: merge commit, squash and merge (one tidy commit) and rebase and merge. Teams usually pick one convention.
  • Run the tests after merging, because two branches can each be fine and still break together.
  • If both sides touched the same lines, you'll get a merge conflict.

08

Rebase

Replay your commits on top of the latest main.

What it does

Rebase lifts your branch's commits off their old starting point and replays them, one by one, on top of the tip of main. Git creates new commits (A′, B′) with the same changes but new IDs. The result is a clean, straight history, as if you'd started your work from today's main.

git switch feature/login
git rebase main
# fix any conflict, then:
git rebase --continue          # or --abort to undo

Considerations

  • The golden rule: don't rebase commits that other people have already pulled. Rebasing rewrites history, and their copies won't match yours.
  • After rebasing a branch you already pushed, you'll need git push --force-with-lease.
  • Conflicts can show up once per replayed commit. Resolve each one, git add, then --continue.
  • git rebase -i (interactive) lets you squash, reorder or reword commits before opening a PR.

09

Merge conflict

Two changes touched the same lines; you choose.

What it does

When two branches change the same lines in different ways, Git can't guess which is right. It pauses the merge and writes both versions into the file between <<<<<<<, ======= and >>>>>>> markers. You edit the file to the correct result, delete the markers, then git add and git commit to finish.

git status                     # lists conflicted files
# edit index.html, remove the markers
git add index.html
git commit                     # completes the merge

Considerations

  • Don't panic. git merge --abort (or git rebase --abort) puts everything back the way it was.
  • The right answer is often a combination of both sides, not just one.
  • Search for leftover <<<<<<< markers before committing. They break code in surprising ways.
  • Prevent conflicts by pulling often and keeping branches small. If you're unsure, talk to whoever wrote the other change.
  • Editors like VS Code show "Accept Current / Incoming / Both" buttons that make this much easier.

10

Pull Request (PR)

"Please review and merge my branch."

What it does

A pull request is a GitHub page that proposes merging your branch into another, usually main. It shows the diff, runs automated checks (tests, linting, previews), and gives teammates a place to comment, suggest changes and approve. Pushing more commits to the branch updates the PR automatically. When it's approved, someone clicks Merge.

git push -u origin feature/login
gh pr create --base main --fill   # or use the GitHub website
gh pr merge --squash

Considerations

  • Small PRs get reviewed faster and more carefully. Aim for something reviewable in about 15 minutes.
  • Say what changed, why, and how to test it. Add screenshots or a recording for UI changes.
  • Write Fixes #42 in the description to link an issue and close it automatically when the PR merges.
  • Open a draft PR early if you want feedback before the work is finished.
  • When reviewing, comment on the code, not the person, and explain the reasons behind your suggestions.

11

Issue

A ticket: bug, feature, or task.

What it does

Issues are GitHub's to-do list for a project: bug reports, feature requests and tasks. Each one has a number (#42), a discussion thread, labels, assignees and milestones. Link an issue to the PR that solves it and it closes itself when that PR merges, which leaves a clear trail from problem to fix.

gh issue create --title "Safari login broken" --label bug
gh issue list --assignee @me
git commit -m "Fix Safari login (fixes #42)"

Considerations

  • A good bug report has steps to reproduce, expected vs. actual behaviour, the environment (browser, OS, version) and screenshots.
  • Use one issue per problem, and search first to avoid duplicates.
  • Agree on a small set of labels and add issue templates so reports arrive consistent.
  • Use GitHub Projects boards to plan and prioritise across many issues.
